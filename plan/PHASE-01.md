## 0.1 — Auth Middleware

**File:** `server/middleware/auth.ts`

### Purpose

Replace `handleServerAction`'s token verification with Hono-compatible middleware. Reads the session cookie, validates the session, and attaches the `Person` to the Hono context.

### Key Constraint

`utils/auth.ts` is a `'use server'` file that calls `cookies()` from `next/headers` — **cannot be imported**. The Session lookup and expiry logic must be **ported** to use `getCookie()` from `hono/cookie`.

### Implementation

```ts
import { Context, Next } from "hono";
import { getCookie } from "hono/cookie";
import { db } from "@/lib/db";
import { errorMSG } from "@/utils/messages";

// Extend Hono's context variable map for type safety
// (declare module augmentation or use c.set/c.get with generics)

export const authMiddleware = async (c: Context, next: Next) => {
  const token = getCookie(c, "token");

  if (!token) {
    return c.json({ error: errorMSG.unauthorized }, 401);
  }

  const session = await db.session.findUnique({ where: { id: token } });

  if (!session) {
    return c.json({ error: errorMSG.unauthorized }, 401);
  }

  // Check expiry (same logic as utils/auth.ts line 29)
  if (session.expireAt.getTime() - Date.now() <= 0) {
    return c.json({ error: errorMSG.sessionExpired }, 401);
  }

  const person = await db.person.findUnique({
    where: { id: session.personId },
  });

  if (!person) {
    return c.json({ error: errorMSG.userNotFound }, 401);
  }

  // Strip password before attaching to context
  const { password, ...safePerson } = person;
  c.set("user", safePerson);

  await next();
};
```

### Context Type Augmentation

Create a shared type file or add to `server/middleware/auth.ts`:

```ts
import { Person } from "@prisma/client";

type SafePerson = Omit<Person, "password">;

declare module "hono" {
  interface ContextVariableMap {
    user: SafePerson;
  }
}
```

This gives `c.get("user")` proper typing across all handlers.

### References to Port From

| Current File | What to Port |
|---|---|
| `utils/auth.ts:14-49` | Session lookup, expiry check, person fetch |
| `app/api/actions/auth/loginUser.ts:37-53` | Cookie attributes (`httpOnly`, `maxAge: 30*24*60*60`) |

### Cookie Attributes to Match

From `loginUser.ts:50-53`:
- Name: `"token"`
- `httpOnly: true`
- `maxAge: 2592000` (30 days in seconds)
- Session ID is a UUID (auto-generated by Prisma `@default(uuid())`)

### CSRF Consideration

Server actions had built-in CSRF. A cookie-authenticated REST API does not. The plan notes to ensure `SameSite=Lax` or `Strict` on the cookie. This should be set during login (Phase 3.5 Auth Module) but the middleware should be aware. For now, document this as a follow-up for the auth module.

### Testing Checklist

- [ ] Request without `token` cookie → 401
- [ ] Request with invalid/expired token → 401
- [ ] Request with valid token → `c.get("user")` returns person (no password field)
- [ ] Password field is never exposed in `c.get("user")`

## 0.2 — Role Guard Middleware

**File:** `server/middleware/requireRole.ts`

### Purpose

Factory function that returns middleware checking `c.get("user").role` against an allowed list. Returns 403 if the role is not permitted.

### Implementation

```ts
import { Context, Next } from "hono";

export const requireRole = (...roles: string[]) => {
  return async (c: Context, next: Next) => {
    const user = c.get("user");
    if (!user) {
      return c.json({ error: "Unauthorized" }, 401);
    }
    if (!roles.includes(user.role)) {
      return c.json({ error: "شما مجوز انجام این عمل را ندارید." }, 403);
    }
    await next();
  };
};
```

### Usage Pattern (in route files)

```ts
import { requireRole } from "@/server/middleware/requireRole";

const adminRoutes = new Hono()
  .use(requireRole("ADMIN"))
  .delete("/:id", deletePersonHandler);
```

Or per-route:

```ts
.post('/', requireRole("ADMIN", "MANAGER"), zValidator('json', schema), handler)
```

| `person-handler.ts:107` | `const requestingUserRole = "ADMIN"` — placeholder replaced by this middleware |

## 0.3 — Error Handling Middleware

**File:** `server/middleware/errorHandler.ts`

### Purpose

Global error handler registered via `app.onError()`. Catches unhandled errors from any route and returns a consistent `{ error: string }` JSON response with appropriate status code.

### Current Problem

Every handler has its own `try/catch` with inconsistent status codes:
- `person-handler.ts:24-27` → 404 for findById errors
- `person-handler.ts:67-70` → 409 for create errors
- `person-handler.ts:83-86` → 404 for update errors
- `person-handler.ts:99-101` → 400 for role update errors

### Implementation

```ts
import { Context } from "hono";
import { HTTPException } from "hono/http-exception";
import { ZodError } from "zod";
import { errorMSG } from "@/utils/messages";

export const errorHandler = (err: Error, c: Context) => {
  // Zod validation errors (from zValidator or manual .parse())
  if (err instanceof ZodError) {
    return c.json(
      { error: errorMSG.invalidInput, details: err.flatten().fieldErrors },
      400
    );
  }

  // Hono HTTP exceptions (from HTTPException throw)
  if (err instanceof HTTPException) {
    return c.json({ error: err.message }, err.status);
  }

  // Domain errors thrown by services (Persian messages)
  // These are plain Error instances with Persian messages
  // We can infer status from the message or default to 500
  console.error("Unhandled error:", err);
  return c.json({ error: err.message || errorMSG.unknownError }, 500);
};
```

### How Handlers Should Change After This

Once the error handler is in place, handlers can **remove** their `try/catch` blocks and let errors propagate. The service layer already throws `new Error(message)` — those will be caught by the global handler.

However, this is a **gradual migration**. Existing handlers can keep their `try/catch` during Phase 0; the error handler acts as a safety net for any uncaught errors. New modules should rely on the global handler and only use `try/catch` when they need a specific status code.

### Status Code Strategy

For service-layer errors, consider one of:
1. **Custom error classes** with a `status` property (cleaner but more boilerplate)
2. **Message-based mapping** in the error handler (fragile)
3. **Keep try/catch in handlers** for status code control (current pattern, pragmatic)

Recommendation: Option 3 for now. The global handler is a safety net, not a replacement for handler-level error control.

### Testing Checklist

- [ ] Unhandled error → 500 with `{ error: "..." }`
- [ ] Zod validation error → 400 with field details
- [ ] HTTPException → matching status code

## 0.4 — Response Helpers

**File:** `server/utils/response.ts`

### Purpose

Standardize JSON response shape across all handlers. Reduces boilerplate and ensures consistency.

### Implementation

```ts
import { Context } from "hono";

interface SuccessResponse<T> {
  message?: string;
  data?: T;
  // Module-specific keys can be added by spreading
}

interface ErrorResponse {
  error: string;
  details?: Record<string, string[]>;
}

export function success<T>(
  c: Context,
  data: T,
  message?: string,
  status: number = 200
) {
  const body: SuccessResponse<T> = { data };
  if (message) body.message = message;
  return c.json(body, status as any);
}

export function error(
  c: Context,
  message: string,
  status: number = 400,
  details?: Record<string, string[]>
) {
  const body: ErrorResponse = { error: message };
  if (details) body.details = details;
  return c.json(body, status as any);
}
```

### Usage Examples

```ts
// Before
return c.json({ message: personLabels.personCreatedSuccessfully, person: personResponse }, 201);

// After
return success(c, { person: personResponse }, personLabels.personCreatedSuccessfully, 201);
```

```ts
// Before
c.status(404);
return c.json({ error: e.message });

// After
return error(c, e.message, 404);
```

### Design Note

The existing handlers use module-specific response keys (`person`, `shop`, `charge`, etc.). The `success` helper returns `{ message, data }`. To maintain backward compatibility with existing `person-client.ts` / `shop-client.ts` which expect `{ message, person }`, either:
- **Option A:** Keep module-specific keys in `data`: `success(c, { person: ... })` → `{ data: { person: ... } }`
- **Option B:** Add an optional `key` param: `success(c, person, "message", 201, "person")` → `{ message, person: ... }`

**Recommendation:** Option A is simpler. Client functions will need minor updates regardless during Phase 5 migration. Use `{ data: { ... } }` consistently going forward.

### Testing Checklist

- [ ] `success(c, data)` → `{ data }` with 200
- [ ] `success(c, data, "msg", 201)` → `{ message: "msg", data }` with 201
- [ ] `error(c, "msg", 404)` → `{ error: "msg" }` with 404

## 0.5 — Pagination Helper

**File:** `server/utils/pagination.ts`

### Purpose

Standardize pagination across list endpoints. Query params: `page` (default 1), `limit` (default 20). Returns `{ data, meta: { total, page, limit, totalPages } }`.

### Implementation

```ts
import { Context } from "hono";

export interface PaginationParams {
  page: number;
  limit: number;
  skip: number;
}

export interface PaginationMeta {
  total: number;
  page: number;
  limit: number;
  totalPages: number;
}

export function getPaginationParams(c: Context): PaginationParams {
  const page = Math.max(1, parseInt(c.req.query("page") || "1", 10));
  const limit = Math.min(100, Math.max(1, parseInt(c.req.query("limit") || "20", 10)));
  const skip = (page - 1) * limit;
  return { page, limit, skip };
}

export function paginatedResponse<T>(
  c: Context,
  data: T[],
  total: number,
  params: PaginationParams
) {
  return c.json({
    data,
    meta: {
      total,
      page: params.page,
      limit: params.limit,
      totalPages: Math.ceil(total / params.limit),
    },
  });
}
```

### Usage Example

```ts
// In handler
const { page, limit, skip } = getPaginationParams(c);
const [data, total] = await db.charge.findManyAndCount({ skip, take: limit });
return paginatedResponse(c, data, total, { page, limit, skip });
```

### Where It Will Be Used

Per HONO-PLAN.md, paginated endpoints:
- `GET /charges` — list all charges
- `GET /payments` — list all payments
- `GET /histories` — list all histories
- `GET /balances/shops` — all shops balance
- `GET /bank/transactions` — all transactions
- `GET /operations` — list all operations

- [ ] No query params → page=1, limit=20
- [ ] `?page=2&limit=10` → correct skip calculation
- [ ] Response includes `meta` with all fields

## 0.7 — Update `server/index.ts`

After all middleware and utils are created, update the Hono entry point to wire them in. This is the final step of Phase 0.

### Changes

```ts
// server/index.ts
import { Hono } from 'hono';
import { authMiddleware } from './middleware/auth';
import { errorHandler } from './middleware/errorHandler';
import { personRoutes } from './modules/persons';
import { shopRoutes } from './modules/shops';

const app = new Hono().basePath('/api');

// Global error handler
app.onError(errorHandler);

// Public routes (none yet — auth module comes in Phase 3.5)

// Protected routes — apply auth middleware
const protectedPaths = ['persons', 'shops'];
for (const p of protectedPaths) {
  app.use(`/${p}{/*}?`, authMiddleware);
}

// Mount routes
app.route('/persons', personRoutes);
app.route('/shops', shopRoutes);

app.get('/', (c) => c.json({ message: 'Ferdowsi API is running!' }));

export { app };
```

### Wildcard Caveat

`app.use('/persons/*', mw)` does **not** match the bare `/persons` path. The `{/*}?` optional-wildcard form (Hono v4) covers both `/persons` and `/persons/anything`. This is critical for protecting `GET /persons` and `POST /persons`.
