# Ferdowsi — Full Application Audit

**Date:** 2026-09-15 · **Method:** 8 parallel read-only agents, partitioned by domain · **Scope:** whole repo
**No files were modified.** Every finding carries a `file:line` reference.

> **Two briefing corrections the agents made:** the database is **PostgreSQL**, not MySQL, and the schema
> **does** carry `@@index` declarations with no migration drift (verified against `prisma/schema.prisma:6`
> and `migration_lock.toml`). Consequences: `SUM(int4)` returns `bigint` in Postgres, so **aggregate overflow
> on balance totals is a non-issue**. But Postgres does **not** auto-index the referencing side of a foreign
> key the way MySQL does, so the missing-index findings are *worse* than first assumed.

---

## Executive summary

| Severity | Count | Theme |
|---|---|---|
| Critical | 18 | Authorization holes; money double-written or silently destroyed |
| High | 31 | Wrong amounts, stale balances, N+1, data-integrity gaps |
| Medium | ~28 | Performance, consistency, UX correctness |
| Low | ~14 | Dead code, hygiene |

**Four systemic root causes** account for most of the Critical list:

1. **`handleServerAction` proves authentication, never authorization.** Several actions check `if (!user)` —
   which can never be false — instead of `user.role !== "ADMIN"`. Server actions are public POST endpoints, and
   there is **no `middleware.ts`** in the repo, so layout guards protect page *rendering* only.
2. **`components/ui/button.tsx:42` never sets `type="button"`.** Every `<Button>` inside a `<form>` is a submit
   button. Three "Close"/"Register" buttons in the money forms therefore write on click.
3. **No mutation invalidates the balance query keys**, and `provider/TanstackProvider.tsx` sets
   `staleTime`/`gcTime` to **1 hour** with all three refetch triggers off. Balances stay wrong for an hour.
4. **Read-then-write with no DB constraint behind it.** Bank-transaction registration, plaque uniqueness,
   duplicate charges, and the one-open-history-span-per-shop invariant are enforced only in application code.

## CRITICAL

### Authorization

**C1. `updateHistory` / `previewHistoryDateChange` have no role check — any logged-in user can rewrite the ownership timeline and trigger a financial recalculation**
`app/api/actions/history/updateHistory.ts:33`, `previewHistoryDateChange.ts:33`

Both wrappers discard the `user` argument entirely. `updateHistory` then calls
`recomputeShopMonthlyCharges(tx, shopId, {apply: true})`, which **deletes and recreates** the shop's charge rows.

> A tenant POSTs `{id, shopId, personId, date, type:"endDate"}` for their own history row. Their accrued charges
> are re-attributed to the owner. Their balance drops to zero; the owner silently inherits the debt.

*(Found independently by the shop/history and auth agents.)*

**C2. `deletePerson` requires only a session, and hard-deletes**
`app/api/actions/person/deletePerson.ts:12`

`if (!user) throw` is a no-op — `handleServerAction` never passes a falsy user. Every sibling action uses
`if (user.role !== "ADMIN") throw`. FKs are `ON DELETE RESTRICT`, so a person with financial history yields a raw
`P2003` shown verbatim to the browser; a person without one is simply destroyed. No confirmation dialog
(`components/person/DeletePerson.tsx:14`). *(3 agents.)*

**C3. Every `Person` read ships the bcrypt password hash to the client**
`findPersonAll.ts:20`, `findPersonByFilter.ts:48`, `findPersonById.ts:20`, `findPersonByShop.ts:20`,
`balance/getPersonBalance.ts:136`, `person/addPersonsFromFile.ts:76`, and — worst — `utils/auth.ts:33`
consumed by the **client** hook `tanstack/query/personQuery.ts:49`.

No query anywhere uses `select` to exclude `password`; a repo-wide grep for `password: false` / `omit` returns
nothing. `findPersonByFilter` takes all-optional filters, so `{}` matches every row.

> Any tenant calls `findPersonByFilter({})` and receives the whole `Person` table: national IDs (which *are* the
> login usernames), phones, addresses, roles, and every ADMIN's bcrypt hash. Separately, `verifyToken` is an RPC
> called from a client component, so the logged-in user's own hash sits in the page payload on every load.

*(4 agents.)*

**C4. The entire bank ledger is readable with no authentication at all**
`bank/getBankTransactions.ts:32`, `getBankCardTransfer.ts:32`, `getBankFailedCardTransfer.ts:32`,
`getBankIncomeTransfer.ts:32`, `reports/getBankTransactionsForReport.ts:25`

None call `verifyToken` or `handleServerAction`. Action IDs ship in the public bundle.

> `POST` with `{startDate:"1900-01-01", endDate:"2100-01-01"}` and no cookie returns every account number,
> sender/receiver account, cheque number, amount and running balance in the system. `limit` is uncapped.

*(3 agents.)*

**C5. Unauthenticated presigned S3 upload URL generator**
`app/api/actions/bucket/GenerateUrl.tsx:17`

No auth check; the caller controls the object key and gets `ACL: "public-read"`, with no size or content-type limit.

> An anonymous caller passes `folderName:"../"`, `fileType:"text/html"` and receives a signed PUT for an arbitrary
> key in the production bucket — overwrite other units' bill images, or host arbitrary content on your domain.

**C6. IDOR — any authenticated user reads any shop's or person's full ledger**
`balance/getShopDetail.ts:41` (accepts `user`, never reads it), `shop/findShopById.ts:13`,
`balance/getPersonBalance.ts:54`, `bank/getTransactionData.ts:13`

`balance/getShopBalance.ts:67` implements the correct check
(`shop.ownerId !== user.id && shop.renterId !== user.id && user.role !== "ADMIN"`) — it is the template these
four are missing.

> A tenant changes the UUID in `/user/shop-detail/<id>/detail` and reads another unit's complete charge and
> payment history. `getPersonBalance` additionally returns the target's password hash (see C3).

### Money written twice, or destroyed

**C7. A bank transaction can be registered more than once — three distinct paths**

- `payment/addPaymentByBankId.ts:68` never checks `bankTransaction.registered` at all; it only looks for an
  existing `Payment`, so a row already consumed as a **Charge** (`addFailedPayment`) or a **Cost**
  (`addCostFromBank`) passes cleanly and has its `referenceId`/`referenceType` silently overwritten.
- `cost-income/addCostFromBank.ts:32` likewise checks only for an existing `Cost`.
- All paths read `registered` **outside** `db.$transaction`, and neither `Payment.bankTransactionId` nor
  `Charge.bankTransactionId` nor `Cost.bankTransactionId` carries `@unique`. Classic TOCTOU.

> Register tx T as a failed-transfer Charge of 50M → then "ثبت دستی" on the same row (still on screen, see C13)
> → a 50M Payment is created for the same T. The shop is both charged and credited 50M from one bank row, and
> the Charge is orphaned from the transaction.
> Or simply double-click submit: both requests read `registered=false`, both insert. 24M credited from one 12M transfer.

**Fix shape:** `updateMany({where:{id, registered:false}, data:{registered:true}})` inside the transaction, bail on
`count === 0`, plus a unique index on each `bankTransactionId`.

**C8. `deletePayment` never un-registers the bank transaction — the money is stranded permanently**
`payment/deletePayment.ts:34`

Nothing in the repo ever writes `registered: false` (verified: the only four writers all write `true`).

> A payment attributed to the wrong shop is deleted to redo it. The shop loses its credit; the bank row stays
> `registered:true` and is therefore filtered out of `/card-transfer` forever. The money is in the bank, absent
> from every balance, and unreachable through the UI. Only a dangling `referenceId` remains.

**C9. The handover day is billed twice — `+1` applied to a half-open span**
`charge/addChargeByShop.ts:78`, `charge/addRentAllKiosks.ts:109`

`updateShopRenter.ts:124` closes the outgoing span with `endDate = newStartDate`, i.e. spans are `[start, end)`.
Both generators compute `differenceInDays(end, start) + 1`. `addChargeToAllShops.ts:105` and `recalcCharges.ts:143`
use the correct arithmetic — **the three generators disagree with each other**.

> 31-day month, owner span ends 1404/05/27, renter starts 1404/05/27 → 27 + 5 = **32 billed days**.
> 11,600,000 becomes 11,974,193 (+3.2%), and 1404/05/27 appears as a charge against both people.
> Every unit with a mid-month tenancy change is over-billed, every month.

**C10. `recalcCharges` deletes a window's charges and recreates nothing when no span covers it**
`charge/recalcCharges.ts:250`

`newList` is empty when no history span overlaps the window, but `changed` is still true — so the `deleteMany`
commits and the `createMany` is skipped. Returns `success: true` with `newAmount: 0`.

> An admin moves a span's `startDate` forward past a billed month. That month's 11,600,000 charge is deleted and
> never replaced. The revenue vanishes from every report with no error.
> `__tests__/charge/recalcCharges.test.ts` covers the no-charge and no-change cases but never this one.

**C11. `<Button>` has no default `type`, so "Close" submits the money forms**
Root cause `components/ui/button.tsx:42` → `bank/CostFromBankForm.tsx:188`,
`payment/AddPaymentBankForm.tsx:260`, `bank/SetRegisterAbleButton.tsx:30`

> A user fills a bank payment, changes their mind, clicks "بستن" — the payment posts against that shop and the
> panel closes immediately, so nothing contradicts their belief that they cancelled. `SetRegisterAbleButton` is
> worse: one click both marks the transaction registerable *and* submits the enclosing payment form. The cost
> form additionally suppresses all toasts (`CostFromBankForm.tsx:62`), so that path is entirely silent.

**C12. `add-charge-to-shop` posts the charge to the wrong shop, or to `shopId: ""`**
`app/(routes)/admin/(charge)/add-charge-to-shop/page.tsx:80`

`dataState.shopId` is written only inside `handleDateChange`; the shop picker updates only `formData`. The guard
reads `formData`, the payload sent is `dataState`.

> Pick month → pick shop → submit sends `shopId:""`. Pick shop A → pick month → switch to B → **charges A** while
> the UI shows B.

**C13. No charge or payment mutation invalidates the balance query keys, and `staleTime` is 1 hour**
`tanstack/mutation/chargeMutation.ts:31,60,89,120,149`; `paymentMutation.ts:54,84,113,143,164`;
`provider/TanstackProvider.tsx` (1h `staleTime`/`gcTime`, `refetchOnMount`/`WindowFocus`/`Reconnect` all false)

`historyMutation.ts:77` invalidates all four balance keys correctly — the convention exists; these ten omit it.

> An operator records a payment, opens the shop's balance to confirm, sees the old debt — and records it again.
> An admin runs the monthly charge generation, then exports the balance report: the export is pre-charge.

**C14. Bulk-import invalidation is a no-op**
`hooks/useChunkedUpload.ts:140`

Callers pass a *list* of keys; react-query reads `["all-persons","all-shops","all-histories"]` as one composite
key, which prefix-matches nothing. It needs a loop of single-key invalidations. Compounded at
`import-proprietor-charge/page.tsx:30`, which names `"all-shops-balance"` — a key that does not exist anywhere
(the real one is `"all-balances"`).

> After an import the admin sees pre-import data on every screen for an hour. Only a full reload fixes it.

**C15. Bulk charge deletion: no confirmation, result never checked, success reported via `toast.error`**
`components/operation/AllOperationsForm.tsx:28` + `operation/deleteChargesByOperation.ts:22`

Two bugs stacked. The UI never inspects `res.success` and always fires `toast.error("با موفقیت حذف شد")`. The
action's `catch` returns from the **transaction callback**, not the function — so the transaction **commits**
whatever already succeeded and the outer `return {success:true}` is unconditional.

> A misclick irreversibly deletes an entire month's billing run. If `operation.update` then fails, the charges are
> already gone, the operation is not flagged deleted, the admin is told it worked, and the button stays live.
> Nothing is invalidated, so the deleted charges remain on screen, hiding the damage.

*(4 agents.)*

**C16. Proprietor-charge import has zero idempotency**
`import/addProprietorChargeFromFile.ts:79` — plain `db.charge.create`, no uniqueness key, no `@@unique` on `Charge`.

> A 300-row import dies at chunk 20 of 30; the admin re-uploads the file. 200 owners are charged twice, with no
> way to distinguish the duplicate from the original.

**C17. A new `Operation` is created per 10-row chunk, so the undo feature can never undo a whole file**
`import/addProprietorChargeFromFile.ts:34`, `addPersonsShopsFromFile.ts:41`, `addKioskFromFile.ts:38`,
with `hooks/useChunkedUpload.ts:51` (`chunkSize = 10`)

> A 300-row import produces 30 identically-titled `Operation` rows. `deleteChargesByOperation` removes 10 charges
> per click. Rolling back a bad import means finding all 30 and getting none of them wrong.

**C18. `"prisma reset": "npx prisma migrate reset"` in `package.json:10`**

`migrate reset` **drops and recreates the database** at whatever `DATABASE_URL` resolves to. `.env*` is gitignored,
so a developer's local env very plausibly holds the production URL. The space in the script name is the only thing
between a tab-complete and total data loss.

## HIGH

### Wrong amounts

- **H1. Kiosk *rent* is counted as مالکانه, and double-counted on the dashboard.** No balance read filters
  `forRent`. `addRentAllKiosks.ts:62` writes rent as `{proprietor:true, forRent:true}`; `getAllShopsBalance.ts:22`
  and `utils/dashboardStats.ts:7` filter on `proprietor` alone. `BALANCE_BUCKETS.proprietor` and `.rent` both
  include `KIOSK` at `proprietor:true`, so the same amount lands in **both** dashboard StatCards.
- **H2. The dashboard "rent debt" card does not match the page it links to.** `dashboardStats.ts:16` uses
  `["KIOSK","BOARD","PARKING"]`; `calculateBalance.ts:208`, which backs the linked page, uses `["BOARD","PARKING"]`.
- **H3. Fractional rial written to an `Int` column.** `addChargeToAllShops.ts:92`, `addChargeByShop.ts:58`,
  `addRentAllKiosks.ts:95` — `totalAmount / totalDays` is never integral, and `createMany` is a single statement
  for all shops, so one fractional row aborts the whole monthly run. `recalcCharges.ts:166` does `Math.round` plus
  remainder absorption correctly; the three generators do neither.
- **H4. No idempotency on any bulk charge generator.** `addChargeToAllShops.ts:53`, `addRentAllKiosks.ts:53`,
  `addAnnualChargeAllShops.ts:33` create a fresh `Operation` with no check for an existing one over the same
  period, and `Charge` has no `@@unique`. Double-click → every shop billed twice for the month.
- **H5. `addPaymentByBankId` trusts a client-supplied amount** (`:27`) and never compares it to the bank row. The
  disabled input is cosmetic. A crafted call credits 2,000,000,000 against a 5,000,000 transaction.
- **H6. `getBankFailedCardTransfer` counts `type:"UNKNOWN"` but lists `type:"PAYMENT"`** (`:66` vs `:75`) →
  `totalPages: 0`, pager hidden, only the first 10 bounced transfers are ever reachable.
- **H7. The user dashboard balance uses the opposite sign and a different universe of rows.**
  `user/getUserQuickState.ts:25` computes `payment − charge` scoped by `personId`; everywhere else is
  `charge − payment` scoped by shop. A tenant owing 50M sees "۰" under a label reading "پرداخت های معوق".
- **H8. PDF export of every all-shops balance page throws.** `store/balanceSlice.ts:104` asks for
  `ownerBalance`/`renterBalance`/`totalBalance`; the exported rows are `{plaque, balance, ownerName, renterName}`.
  `formatNumber(undefined).toString()` → TypeError. The real `balance` field is referenced by no column.
- **H9. The minimum-debt filter filters the export but not the screen.** `store/balanceSlice.ts:89` — zero readers
  of `allBalanceFiltered` outside the exporter. Screen and downloaded report disagree about who owes money.
- **H10. Rent billing keys off the stale `ShopHistory.shopType`.** `updateShopInfo.ts:38` changes `Shop.type` and
  cascades nothing, so a STORE→KIOSK reclassification is skipped by the rent run forever (`charge/utils.ts:38`).
- **H11. Plaque changes are not propagated** to `ShopHistory.plaque` / `Charge.plaque` / `Payment.plaque`
  (`updateShopInfo.ts:30`). Contrast `updatePerson.ts:53`, which cascades names correctly in one `$transaction`.
- **H12. `parseNumber` turns unparseable amounts into `0`.** `components/upload-file/readFile.ts:79` strips only
  the ASCII comma, so Persian digits `۱۲٬۵۰۰٬۰۰۰` → `NaN` → `0` → a real BankTransaction with amount 0. Because
  `balance` is part of `bankRowHash`, re-importing the corrected file inserts a **second** row — a permanent
  duplicate that the whole hash design exists to prevent.
- **H13. Legacy `addBankData` writes no `rowHash`** (`:68`). `rowHash` is `String? @unique` and Postgres allows
  unlimited NULLs, so every row that importer writes is exempt from the unique index. Import via the old page and
  then the net-bank page → the whole statement lands twice.
- **H14. Import zod schemas are declared but never executed.** `schema/importSchema.ts:7,35` are referenced only by
  their own `z.infer` aliases. Raw XLSX JSON goes straight into Prisma, and `row.type as ShopType` is an unchecked cast.

### History and integrity

- **H15. `updateShopStatus` writes the new *open* span with `isActive: false`** (`:99`) — `isActive` and `endDate`
  permanently contradict, and the UI badges the live period as closed.
- **H16. Renting out an inactive shop creates two overlapping open spans.** `updateShopRenter.ts:59` never looks
  for an open `InActive` row, and `recalcCharges` sums both → ~60 billable days in a 30-day month.
- **H17. An empty `renterId` closes the owner span and opens nothing.** `shopSchema.ts:68` types it `z.string()`,
  so `""` validates and the `if (renterId && !newRenter)` guard is skipped → a permanent gap in the timeline.
- **H18. No constraint prevents two open spans per shop.** Five separate read-then-write call sites enforce it.
  Postgres can: `CREATE UNIQUE INDEX ... ON "ShopHistory"("shopId","type") WHERE "endDate" IS NULL`.
- **H19. Sessions are never deleted.** No `session.delete`/`deleteMany` anywhere. Logout removes only the cookie;
  a password change does not invalidate (`updatePersonPassword.tsx:53`). The cookie has **no `secure`, no
  `sameSite`**, a 30-day `maxAge`, and `nginx.conf:40` listens on port 80 only.
- **H20. Deactivated accounts can still log in.** `Person.isActive` is read nowhere in `loginUser` or `verifyToken`.
- **H21. No rate limiting or lockout on login, plus user enumeration.** `loginUser.ts:26` returns distinct
  `userNotFound` vs `invalidPassword`, and the not-found path returns *before* the ~250ms bcrypt cost, so existence
  is measurable even if the messages were unified. National IDs are a checksummed 10-digit space.
- **H22. Bulk-imported users get their phone number as their password** (`addPersonsFromFile.ts:33`). Combined with
  C3, which returns `phoneOne` for everyone, this is a full account-takeover primitive.
- **H23. `addPersonsFromFile` builds a `new PrismaClient()` per call** (`:22`), never `$disconnect`s, and wraps the
  whole file in one interactive transaction with no `timeout` → Prisma's 5s default → `P2028` → the entire import
  rolls back. Repeated imports exhaust the connection pool and take the app down.
- **H24. Nothing in the deploy pipeline runs `prisma migrate deploy`.** The `Dockerfile` has no migrate step;
  `postinstall` runs `generate` only. Migrations are being applied by hand.

### Frontend

- **H25. Zustand survives logout.** `components/LogoutButton.tsx:13` clears react-query and the cookie but not the
  store, and both logout and login are client-side navigations. On a shared machine,
  `update-password/page.tsx:80` reads `userId: userInfo?.IdNumber` from the stale store — **user B changing their
  password can target user A's account.**
- **H26. Loading/error guards create JSX but never `return` it** (`payment-by-shop/page.tsx:61`). A failed shop
  fetch renders a normal, empty page with no error and no retry.
- **H27. Pages render zustand state rather than the query** (`payment-by-shop/page.tsx:100`, `payment-by-person`,
  `find-charge-by-shop/page.tsx:92`, `shop-balance/[id]/page.tsx:38`) → shop B's page shows shop A's rows.
- **H28. Queries fire with an empty id** — no `enabled` guard on `useFindChargesByShop`/`ByPerson`,
  `useFindPaymentsByShop`/`ByPerson`, and the `""` result is cached for an hour. `balanceQuery.ts` gets it right.

### Performance

- **H29. `getShopBalance` re-queries per person for data already in memory** (`:163`) — 12+ queries, and the full
  ledger fetched twice, on every shop-balance page load.
- **H30. `findAllShopsByPerson` is ~4 queries per unit with full row fetches** (`:50`) — an owner with 20 units
  pulls ~24,000 rows to produce 40 numbers. `getPersonBalance.ts:75` shows the `groupBy` form that fixes it.
- **H31. Per-row `$transaction` in a loop** in `addBankData`, `addPersonsShopsFromFile`, `addKioskFromFile` — 3–6
  round trips per row, plus a bcrypt hash per row even when the person already exists. `addNetBankData.ts:135` is
  the only importer using `createMany` + `skipDuplicates`.

## Missing indexes

Postgres does **not** auto-index the referencing side of a foreign key.

| Table | Missing | Scanned by |
|---|---|---|
| `Shop` | `(ownerId)`, `(renterId)` | every user dashboard load — `findAllShopsByPerson.ts:43,47` |
| `Charge` | `(date)`, `(shopId, date)` | `getAllCharges.ts:22`, `calculateBalance.ts:25`, `getChargesByShop.ts:25` |
| `Payment` | `(date)`, `(shopId, date)` | `getAllPayments.ts:22`, `calculateBalance.ts:31` |
| `ShopHistory` | `(shopId, type, endDate)` | every owner/renter/status change — 5 call sites |
| `ShopHistory` | `(isActive, startDate)`, `(type)`, `(endDate)` | `charge/utils.ts:69` — full scan on every monthly run |
| `BankTransaction` | `(registered, registerAble, type)` | all four paginated bank views |
| `Payment` / `Charge` / `Cost` | `(bankTransactionId)` | every registration click — also the natural `@unique` for C7 |
| `Cost`, `Income` | `(date)` | `getAllCosts.ts:63` |
| `Session` | `(expireAt)` | needed once a pruning job exists |

Present and correct: `Charge(operationId/shopId/personId)`, `Payment(shopId/personId)`,
`ShopHistory(shopId/personId)`, `ShopChargeReference(shopId/year)` + `@@unique([shopId,proprietor])`,
`BankTransaction(recieverAccount/date/referenceId)` + `@@unique(rowHash)`, `Shop.plaque`, `Person.IdNumber`.

## Notable MEDIUM findings

- **`GET /api/add-bank-category`** (`route.ts:5`) — a mutating GET with an unbounded N+1 loop and an empty `catch`.
  One prefetch or link-preview bot overwrites the `category` of every registered transaction from `accountType`
  alone, discarding the per-registration categories `addCostFromBank.ts:60` sets. It is a one-off backfill left
  mounted as a route; it belongs in `scripts/`. *(3 agents.)*
- **`Cost.amount` / `Income.amount` are `Int` with no zod upper bound** (`cost-IncomeSchema.ts:9`). The largest
  expenses in the system — a 3,000,000,000-rial invoice — are exactly the ones that cannot be recorded.
  `utils/bankAmount.ts:6` already documents that these were "deliberately still Int".
- **`ShopChargeReference.year` mixes Jalali and Gregorian.** `shopAnnualChargeReference.ts:42` writes
  `new Date().getFullYear()` (2026); `shopChargeReference.ts:59` writes `currentJalaliYear()` (1405). Same column.
- **Reference regeneration is global and unscoped** (`shopChargeReference.ts:160` — `deleteMany` with no `year`,
  no `shopId`), and `@@unique([shopId, proprietor])` makes multi-year retention impossible. A back-dated charge run
  silently bills the old month at the new year's rates.
- **`Operation`s are created outside the transaction** in four generators → orphaned operations on every failure path.
- **Manual payment dates are stored at local midnight** (`addPayment.ts:70`) while every bank-imported row sits at
  UTC midnight. `utils/jalaliRange.ts` documents the convention; `addPayment` does not follow it. Tehran +3:30 → a
  payment lands on the previous calendar day, and a month-boundary payment in the wrong month.
- **The dashboard "last 30 days" window uses server-local wall-clock time** (`getAdminDashboard.ts:72`) against
  UTC-midnight rows, so the recent-activity numbers change with the hour of day.
- **Weekly `pg_dump` pushed unencrypted into a second git repo** (`.github/workflows/db-backup.yml:24`) — national
  IDs, phones, addresses, bcrypt hashes and the full ledger, with no rotation. Verify that repo's visibility and
  encrypt with age/gpg before committing. *(The target repo is behind a secret, so its visibility is unverified.)*
- **The bank report buckets by category while ignoring `type`** (`utils/bankReportCalculations.ts:78`): a refunded
  rent shows as revenue, and `type:"UNKNOWN"` rows are counted in `totalTransactions` but in neither total.
- **Soft-delete flags unfiltered at three read sites** — `Operation.deleted` (`getAllOperations.ts:21`),
  `Person.visable` (`findPersonByFilter.ts:48`, which surfaces the hidden bootstrap admin), `Shop.isActive` (nowhere).
- **`Float` for `Shop.area` feeds rial arithmetic** (`schema.prisma:14`). `Math.round` at 100,000 granularity
  absorbs it except on a `.5` boundary, which shifts one shop's annual charge by 100,000. `Decimal(10,2)` is correct.
- **Three number-format conventions coexist**, including bare `.toLocaleString()` with no locale — which renders
  differently per machine and between SSR and client. ~25 sites.
- **Resident names and amounts logged to stdout** — `addChargeToAllShops.ts:76` logs a full `ShopHistory` including
  `personName`; `addPersonsFromFile.ts:20` logs national IDs and plaintext passwords.
- **No `error.tsx` / `loading.tsx` / `not-found.tsx` anywhere** across 81 route files.
- **No file-size, MIME, or row-count limit on any data import.** `UploadImage.tsx:52` checks 2MB and an allowlist;
  the data importers check nothing.
- **`MANAGER` is admitted to all of `/admin`** (`admin/layout.tsx:17`) but every mutation requires strict `ADMIN`,
  and `getShopBalance.ts:67` locks MANAGER out of the per-shop pages the dashboard links to.
- **`handleServerAction.ts:36` computes `isProduction` and never uses it** → raw Prisma messages (constraint names,
  column names, sometimes parameter values) reach the browser in production.
- **`endShopRenter` accepts a `renterId` and never checks it against the shop** (`:46`). The Hono rewrite it
